Purpose

This implementation guide documents a proof of concept that turns an HL7 v2 scheduling feed into FHIR R4 resources conforming to AU Core 2.0.0. A Python ingestion service receives SIU S12, S13, S14 and S15 messages, converts them, and writes them to a HAPI FHIR server. A web front end (planned: Vue/Vuetify) reads appointments directly from that server.

This guide describes a proof of concept that uses simulated data only. It is not intended for clinical use. IHI, HPI-I and Medicare numbers in the examples are synthetic: they pass the AU Base format checks but were not issued to anyone. The canonical URL, local identifier systems and local code systems are example.org placeholders.

What conforms to what

Resource Profile Populated from
Patient AU Core Patient PID
Practitioner AU Core Practitioner AIP-3
Location AU Core Location AIL-3, AIL-4
Organization AU Core Organization AIL-3.4 facility, looked up on the FHIR server
Appointment SIU AU Appointment (this guide) SCH, AIS, AIG, AIL, AIP, NTE

AU Core 2.0.0 has no Appointment profile, so this guide defines one whose participants reference the AU Core resources.

Scope

Event Meaning Effect
S12 New appointment booking Create the Appointment (or update it if the ID already exists)
S13 Reschedule Rebuild the Appointment with the new times
S14 Modification Rebuild the Appointment with the changed details
S15 Cancellation Set status to cancelled and record the reason

How to read this guide

  • AU Core Conformance: what changes compared with a plain FHIR R4 mapping, and why.
  • Mapping: field-level HL7 v2 to FHIR rules.
  • Local Registry: local configuration (location type translations), and how facilities and MRN namespaces are handled without it.
  • Processing: matching, ordering and acknowledgements.
  • Worked Example: one appointment through S12 → S13 → S14 → S15, plus a missing-data example.
  • Building This Guide: local build and the GitHub Pages workflow.
